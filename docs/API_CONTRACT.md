# API contract (Phase 1 baseline through Phase 2D.2)

This document records the HTTP interface implemented by `backend/src/app.ts` and the compatibility boundary for provider routing. JSON failures use `{ "error": string }`; unexpected server failures also include `requestId`. Successful responses continue to use the existing shapes.

## Authentication and session

All protected routes authenticate the HTTP-only `session` cookie. Missing/expired/revoked sessions return `401 { error, code }`. Cookies are `SameSite=Lax`, `Secure` in production, and expire after 24 hours for guests or seven days for registered sessions.

| Method / path | Request | Success |
|---|---|---|
| `GET /api/auth/me` | none | `{ user: { id, email, isGuest }, provider, guestDailyMessageLimit }` |
| `POST /api/auth/guest` | none | Sets cookie; `{ user, provider, guestDailyMessageLimit }` |
| `POST /api/auth/register` | `{ email, password }`; email normalized/lowercase, password 10–128 chars | `201 { user }`, may convert current guest to registered account |
| `POST /api/auth/login` | `{ email, password }`; same schema | `{ user }` and cookie |
| `POST /api/auth/logout` | none | `204`; revokes current session |
| `POST /api/auth/logout-all` | none | `204`; revokes all sessions |

Guest creation does not create a `UserSettings` row or persist account defaults. Upgrading that guest to a registered account creates settings with `selectionMode: "AUTO"`; pre-existing registered settings and conversations remain `MANUAL` after migration.

## Models and account settings

`GET /api/models` returns `{ models, activeProvider }`. Each model entry has a stable application `id`, `provider`, provider-specific `model`, `label`, `description`, `available`, `availability`, `capabilities`, `contextWindow`, `maxOutputTokens`, `parameters` constraints, and declared task suitability/evaluation evidence where available. Missing quality evidence is represented as unknown; the catalog does not imply an objective ranking. The endpoint never contains credentials. Unconfigured Gemini models may be omitted from the selectable catalog; a saved model preference is still returned by `/api/settings` with an unavailable reason. `activeProvider` is `null` when no live provider or explicitly enabled development mock is configured.

The registered-account settings API uses the existing `UserSettings` row; it does not create a second settings record. Guests receive `403 SETTINGS_REGISTERED_ACCOUNT_REQUIRED` for both routes and continue to choose model/parameters per request.

| Method / path | Request | Success |
|---|---|---|
| `GET /api/settings` | none | `{ settings: { selectionMode, defaultModelId, defaultModelAvailability: { status, modelId }, temperature: number \| null, temperatureSupported: boolean \| null, responsePreferences, memoryEnabled } }` |
| `PATCH /api/settings` | Partial strict object: `{ selectionMode?, defaultModelId?, temperature?: number \| null, responsePreferences?, memoryEnabled? }` | `{ settings }` with the same shape |
| `GET /api/memory/settings` | none | `{ memoryEnabled }` |
| `PATCH /api/memory/settings` | `{ memoryEnabled: boolean }` | `{ memoryEnabled }` |

`selectionMode` is `AUTO` or `MANUAL`. `defaultModelId` maps to the existing provider/model columns; `temperature`, `responsePreferences`, and `memoryEnabled` reuse their existing columns. `temperature: null` clears a saved sampling preference so the provider's own default applies; new account settings begin with no sampling override. The additive migration makes the existing temperature column nullable without changing existing values. `temperatureSupported` is `null` when no sampling preference is saved. `defaultModelAvailability.status` is `available`, `provider_not_configured`, `disabled`, or `model_not_found`. A saved default that becomes unavailable is preserved; unrelated patches do not erase it. Selecting an unknown model returns `400 MODEL_NOT_FOUND`; selecting a known but disabled/unconfigured model returns `503 MODEL_UNAVAILABLE`. Invalid values return `400 VALIDATION_ERROR`. Temperature must be declared by the model registry and inside its range; unsupported values return `400 UNSUPPORTED_PARAMETER`, and a persisted value no longer applicable to a selected model is reported as `409 SAVED_PARAMETER_UNSUPPORTED`. The API does not silently replace a provider/model or drop a saved parameter. `/api/memory/settings` remains a compatible view of the same `memoryEnabled` value. Guest requests never read registered-account settings, including response preferences.

## Conversations and messages

| Method / path | Request | Success |
|---|---|---|
| `GET /api/conversations` | none | `{ conversations: Conversation[] }`; only the authenticated user's rows |
| `POST /api/conversations` | `{}` | `201 { conversation }` |
| `PATCH /api/conversations/:id` | `{ title }`; trimmed, 1–80 chars | `{ ok: true }` |
| `PATCH /api/conversations/:id/model-selection` | `{ selectionMode: "AUTO" }` or `{ selectionMode: "MANUAL", selectionModelId?: string }` | `{ conversation }` |
| `DELETE /api/conversations/:id` | none | `204` |
| `PATCH /api/messages/:id` | `{ content }`; trimmed, 1–20,000 chars | `{ ok: true }` |
| `GET /api/usage` | Optional bounded filters and pagination; see Usage reporting | `{ usage, totalEstimatedCost, recentEstimatedCostByCurrency, totalCount, pagination, period }` |

Unknown or non-owned conversations/messages return `404`. Editing while generation is active returns `409`.

New registered-account conversations inherit the account selection mode. When that mode is `MANUAL`, the account default model is copied into the dedicated `selectionModelId`; `Conversation.provider/model` continue to mean the latest actual response model. Existing conversations migrate to `MANUAL` with a nullable `selectionModelId`; a null selection uses the account manual default, and unavailable saved choices remain stored until explicitly changed. A legacy registered account without a `UserSettings` row gets a `MANUAL` conversation with no saved model, so the configured-default compatibility path remains available. Guest conversations are always `MANUAL` with no persisted selection model. Guests may choose a model and parameters per request, but cannot persist account or conversation selection preferences or receive account response preferences; their per-request model override is applied only to that request. The conversation model-selection route is registered-account-only; guests receive `403 GUEST_CONVERSATION_SELECTION_UNAVAILABLE`.

## Chat streaming

`POST /api/chat/stream` is authenticated and accepts `{ conversationId?: UUID, content?: string, selectionMode?: "AUTO" | "MANUAL", modelId?: string, parameters?: object, taskType?: public task type, regenerate?: boolean }`. Content, when present, is trimmed and 1–240,000 chars. Either content or a conversation ID with `regenerate: true` is required. Every explicit parameter must be supported by the selected model and within its declared numeric range. Guest quota exhaustion returns `429`; a busy conversation returns `409`; an unknown/non-owned conversation returns `404`. Assistant messages retain actual provider/model in `provider`/`model`; nullable routing audit fields are `requestedSelectionMode`, `requestedModelId`, `taskType`, `routingPolicyVersion`, and `routingReasonCode`.

Selection precedence remains: (1) explicit per-request selection; (2) persisted conversation selection; (3) registered-account default; (4) legacy configured-default behavior when no persisted selection exists. A supplied `modelId` without `selectionMode` is a legacy Manual request and is honored exactly for that request; it does not update the conversation preference. That one-shot explicit model request uses request parameters and does not inherit saved account generation parameters. `selectionMode: "AUTO"` with `modelId` is rejected as `400 SELECTION_CONFLICT`. Manual mode resolves the explicit request model, otherwise the conversation's saved manual model, otherwise the registered account's saved default, and only then the legacy configured default. Unknown and unavailable selections return actionable `MODEL_NOT_FOUND`/`MODEL_UNAVAILABLE` errors without substitution. For a persisted Manual selection, saved account temperature is sent when the request does not explicitly provide a model or temperature; if the selected model does not support it, the request returns `409 SAVED_PARAMETER_UNSUPPORTED` instead of dropping the value. Explicit request parameters are validated against the model registry.

In Auto mode the deterministic classifier assigns a task profile, with `general_conversation` as the uncertain/default result. Public request task overrides are restricted to `general_conversation`, `complex_reasoning`, `coding`, `writing`, `document_analysis`, `research`, `vision`, `structured_extraction`, and `tool_intensive`; internal summarization and memory-extraction operations are not public chat overrides. Classification does not grant a capability: unsupported input requirements such as vision, live web research, structured-output enforcement, or tool execution return `422 TASK_CAPABILITY_UNAVAILABLE` unless an eligible registered adapter explicitly supports them. Current model metadata does not claim unsupported capabilities. Gemini 3.8 Flash does not advertise temperature or top-p sampling parameters; requests that try to send them directly to its adapter fail as `400 UNSUPPORTED_PARAMETER` rather than being silently omitted. A new Auto account with no saved temperature can therefore use Gemini's provider defaults.

The router filters configured, enabled models by required capabilities, supported parameters, model context/output bounds and provider availability before ranking. It considers measured task suitability/quality evidence when present; absent evidence remains unknown, so a documented server-configured preference may break a tie but is not represented as a measured quality score. Cost and latency are constraints or tie-breakers only among candidates with comparable quality evidence. Routing policy is versioned in server configuration. The router runs before authoritative model-specific ContextBuilder processing; Auto may prepare another eligible context/model before the first text delta if the selected context cannot fit. Manual returns an actionable context error. No model switch occurs after a text delta.

Auto may retry a different eligible, configured, non-mock provider only for classified retryable provider failures before the first response text delta. Authentication/configuration, validation, context, policy and other non-retryable errors do not fall back. Manual never falls back; production never routes to mock. The server sends one `meta` event only after the selected attempt is fixed, then emits deltas from that attempt. Metadata includes actual provider/model, requested mode, task type, routing policy version, a safe reason code, and whether a pre-delta fallback occurred.

Successful requests use `Content-Type: text/event-stream`. Existing SSE events remain:

- `meta`: `{ conversationId, userMessageId, assistantMessageId, provider, model, mock, requestedSelectionMode, taskType, routingPolicyVersion, routingReasonCode, fallbackOccurred }`
- `delta`: `{ text }`
- `done`: `{ status, inputTokens, outputTokens, estimatedInputTokens, estimatedOutputTokens, usageStatus, estimatedCost, pricingCurrency }`; provider-reported counts and estimates remain separate, and unavailable provider usage is not represented as zero. `pricingCurrency` is the snapshot currency (default `USD`) or null when no pricing applies.
- `error`: `{ error, code, partial }`

`status` is `complete`, `partial`, or `cancelled`. The server atomically persists the terminal assistant row and a durable usage-outbox event before sending `done`; `UsageRecord` delivery is idempotent and may be retried asynchronously. Provider/model errors before headers use JSON `{ error, code }` and an appropriate HTTP status; failures after streaming begins use `error` with the same `code`. Stable selection/routing errors include `400 MODEL_NOT_FOUND`, `503 MODEL_UNAVAILABLE`, `400 UNSUPPORTED_PARAMETER`, `409 SAVED_PARAMETER_UNSUPPORTED`, `400 SELECTION_CONFLICT`, `422 TASK_CAPABILITY_UNAVAILABLE`, and `503 NO_ELIGIBLE_MODEL`. No unknown ID is replaced by a default model.

Each provider attempt has a unique ID and an idempotent usage event. Successful assistant response usage remains associated with its message; failed pre-delta attempts are accounted independently. Provider-reported usage is recorded as actual provider usage. When unavailable, token/cost values are null with an explicit unknown usage status rather than zero. Estimated values are separately marked estimates and must not be described as provider-reported. Duplicate deliveries are prevented by unique idempotency keys.

## Phase 2B context handling

The chat `content` validation limit is 240,000 characters (the existing JSON body limit still applies). The message-edit endpoint has its separate 20,000-character limit. The backend builds provider context from the selected model's context window and output limit, keeps complete recent user/assistant turns in chronological order, and applies account response preferences as provider system instructions. If the current message and required instructions cannot fit after output and safety reserves, `POST /api/chat/stream` returns HTTP 413 with `{ "error": "...", "code": "CONTEXT_TOO_LARGE" }` before opening an SSE response. Token diagnostics are server logs only and contain counts/IDs, never message content or preferences. No database schema changes are required for this context behavior.

## Phase 2C.1 conversation summaries

The HTTP chat request and SSE event contract is unchanged. Summaries and their durable jobs are internal and are not exposed by conversation APIs. When a completed chat crosses the configured context threshold, PostgreSQL queues summary work in the same transaction that finalizes the assistant message and enqueues its usage event. A valid summary is supplied to the existing ContextBuilder as an explicitly untrusted context message; raw messages at or below `coveredThroughSequence` are not sent again. Original messages remain stored. Summary generation uses the explicitly configured `SUMMARY_MODEL_ID`; provider errors do not switch models and failed jobs retry with backoff. `GET /api/usage` includes an `operation` field (`chat`, `summary`, or `memory_extraction`) while preserving its prior fields.

## Compatibility and validation

The frontend continues to use `/api/models` as its sole model catalog. Existing clients may omit `modelId`; after persisted conversation and registered-account preferences are resolved, the backend retains configured-default behavior as the final fallback. An explicitly supplied unknown or unavailable ID is rejected. `Conversation.provider` and `Conversation.model` represent the latest actual response provider and provider-specific model; `Conversation.selectionMode` and `selectionModelId` represent conversation preference. Provider-specific payloads and credentials remain server-side.

The local mock provider is registered only when `MOCK_PROVIDER_ENABLED=true` and `NODE_ENV` is `development` or `test`. Production rejects this setting and never advertises/routes to mock. With no configured live provider and mock disabled, the model catalog reports live models unavailable and chat returns `503 MODEL_UNAVAILABLE`; authentication/settings remain available. Development and test fixtures must opt into mock explicitly.

Usage `estimatedCost` is an estimate calculated once from the pricing configuration active at usage-event creation and persisted in the outbox/usage row. Current configuration defaults to USD and may use another currency only when matching non-USD rates are explicitly configured. Reads do not recalculate stored values after rates change. Estimates exclude cached-token discounts and provider billing adjustments and are not invoices or actual provider charges.

## Usage reporting and pricing provenance

`GET /api/usage` requires an authenticated session and every record and aggregate is scoped to the authenticated user's `userId`. It accepts `from` and `to` as inclusive UTC calendar dates (`YYYY-MM-DD`), `provider` (1–40 ASCII letters, digits, underscore or hyphen), `model` (1–120 characters), `operation` (`chat`, `summary`, `memory_extraction`, or `provider_attempt`), `usageStatus` (`provider_reported`, `estimated`, `partial`, `unknown`, or `legacy`), `limit` (1–100, default 100), and an opaque `cursor`. Invalid filters/cursors and date ranges over 366 UTC days return `400 { error, code: "VALIDATION_ERROR", requestId }`.

When either date bound is supplied, the usage history is restricted to the inclusive range. A missing bound is inferred to make a 30-day inclusive range. Without date parameters, the backward-compatible `usage` history remains unbounded except for its existing recent-100 default. Cursor pages sort by `createdAt DESC, id DESC`; `pagination.nextCursor` is null when there are no more rows. `totalCount` covers all matching history, not only the current page.

The `period` aggregate is independent of pagination and defaults to the most recent 30 UTC calendar dates (today included). Explicit date bounds and provider/model/operation/status filters apply to the aggregate. The aggregate includes request and event counts, separate provider-reported and estimated token totals, usage-status counts, provider/model/operation breakdowns, and provider-attempt/failure counts. A `chat` operation filter includes its `provider_attempt` events; attempt records remain labeled `provider_attempt` in history and breakdowns. `requestCount` excludes those attempt events. Costs are summed per currency. `period.totalEstimatedCost` is null when multiple currencies or any unknown-cost records prevent a complete single-currency total; the currency buckets expose known subtotals and unknown amounts.

Breakdown entries retain their dimension-specific property names: `providerBreakdown` entries contain `{ provider, recordCount, estimatedCostByCurrency }`, `modelBreakdown` entries contain `{ model, recordCount, estimatedCostByCurrency }`, and `operationBreakdown` entries contain `{ operation, recordCount, estimatedCostByCurrency }`. Each currency bucket contains `{ currency, estimatedCost, pricedRecordCount, unknownCostRecordCount }`.

For compatibility, the top-level `totalEstimatedCost` remains the estimate subtotal for the newest 100 rows matching the history filters, irrespective of which cursor page is shown; it is not a lifetime or selected-period total. `recentEstimatedCostByCurrency` makes this subtotal safe to display when currency settings differ. The dashboard uses `period`, not this legacy field, for its selected-period view.

Each new `UsageOutbox` event captures `pricingCurrency`, `pricingVersion`, and `pricingEffectiveAt` when it is enqueued; delivery retries copy that exact snapshot to `UsageRecord`. The version contains the configured pricing label and a fingerprint of the applicable currency/rates so a rate change yields a different version. If `PRICING_EFFECTIVE_AT` is set, it supplies the configured schedule's activation time; otherwise the process records when it loaded the snapshot. That timestamp is platform pricing provenance, not a claim about the provider's official effective date. The existing USD cost/rate configuration remains supported; non-USD schedules require explicit generic per-million input/output rates. Historical estimated costs are not recalculated. Legacy rows are marked USD because the prior API contract computed them in USD; their unknown version and effective time remain null. Assistant `Message.pricingCurrency` preserves the currency displayed alongside its stored per-response estimate; usage outbox/record rows remain authoritative for pricing version and audit dates. Provider-reported token counts and token estimates remain separate. Unknown provider usage is never converted to zero. Costs remain estimates, not provider bills.

The current configured USD rates can be checked against the providers' primary pricing pages: [OpenAI API pricing](https://developers.openai.com/api/docs/pricing) and [Gemini API pricing](https://ai.google.dev/gemini-api/docs/pricing). Cached-token discounts, grounding/tool charges, taxes, regional uplifts, account-specific discounts, and provider billing corrections are outside this token-only estimate unless separately represented by the configured pricing model.

## Phase 2C.2 long-term memory (additive)

Memory endpoints require an authenticated **registered** account. Guests receive `403 { error, code: "MEMORY_REGISTERED_ACCOUNT_REQUIRED" }`. Existing `UserSettings.memoryEnabled` remains the sole retrieval/suggestion setting and defaults to `false`. `GET /api/memory/settings` returns `{ memoryEnabled }`; `PATCH` accepts `{ memoryEnabled: boolean }` and returns the same shape. Turning the setting off immediately suppresses retrieval and suggestion generation; manual memory management remains available.

`GET /api/memories` returns `{ memories: [{ id, content, category, tags, createdAt, updatedAt, lastRetrievedAt, retrievalCount }] }`. `POST /api/memories` accepts `{ content, category, tags? }` and returns `201 { memory }`. `PATCH /api/memories/:id` accepts any non-empty subset of those fields and returns `{ memory }`; `DELETE` returns `204`. Content is trimmed and limited to 2,000 characters; category is a validated generic Unicode label of 1–40 characters (the UI offers `preferences`, `technical_skills`, `work_projects`, `communication_preferences`, `goals`, and `other` as starting labels, while custom labels remain supported); at most 10 trimmed tags of at most 32 characters are accepted. Obvious secret patterns are rejected with `400 MEMORY_SENSITIVE_CONTENT`; this deterministic filter cannot detect every sensitive detail. Missing or non-owned IDs return `404 MEMORY_NOT_FOUND`.

`GET /api/memory/suggestions` returns `{ suggestions }`, with each pending suggestion's exact proposed content, category, tags, optional source conversation title, and expiry. `POST /api/memory/suggestions/generate` accepts `{ conversationId }` and explicitly asks the provider-independent extractor to inspect that owned conversation. It is rate limited, requires memory to be enabled, validates structured output and confidence/usefulness thresholds, and creates only pending suggestions. It never creates an approved memory. `POST /api/memory/suggestions/:id/approve` accepts `{ content?, category?, tags? }`; the exact resulting values are returned as `{ suggestion, memory }`. Approval is transactional and idempotent. `POST .../:id/reject` returns `{ suggestion }`; expired pending suggestions return `410 MEMORY_SUGGESTION_EXPIRED`. Suggestions are visible exactly as proposed before approval and can be edited in the approval request. User-approved memories and suggestions are always owner-scoped.

Retrieval uses parameterized PostgreSQL full-text queries with a GIN-indexed `tsvector` maintained from content and tags using the `simple` configuration, ownership filtering, a minimum lexical rank, limited recency influence, and bounded top-K/total/per-memory token budgets. The configuration avoids English stemming and supports token matching such as the tested English, Spanish and French examples, but it does not infer synonyms or semantic similarity and is not claimed to work equally well for every language or writing system. It is disabled by default, never runs for guests, and is not cached. Retrieved memory text is a labeled user-role reference block before the raw conversation; system instructions state that neither summaries nor memory may provide instructions, and the current user turn remains last. Memory candidates are added only after recent raw turns and the summary fit. Extraction is explicitly user-triggered from a conversation, rather than invoked after every chat turn; it has a per-user PostgreSQL hourly rate limit and expiry, treats transcript text as untrusted input, redacts recognized credential patterns before provider submission, and validates candidate content before persistence. These deterministic checks do not detect all sensitive data. Extraction uses the conversation's configured provider/model through the common `AIProvider.generate` interface and records estimated provider usage using the existing durable usage outbox (`operation: "memory_extraction"`). In local mock mode extraction produces no candidates; it is not live-provider verification.
